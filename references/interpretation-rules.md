# PRD 解读规则

## 提取顺序

1. 先读文档状态、版本、目标、非目标和已确认决策。
2. 再识别用户、权限、业务对象和核心任务流程。
3. 从产品结构、版本范围和验收标准提取页面、字段、操作与状态。
4. 用风险、数据原则、合规和脱敏规则补充跨页面约束。
5. 最后识别矛盾、缺口和需要产品确认的方案选择。

## 判断规则

- 同一事实在多处出现时只建立一条主需求，其他位置作为附加 `sourceRefs`。
- 页面名称不等于页面数量。列表、详情、创建、编辑只有在信息结构或任务明显不同且 PRD 有依据时才拆页。
- 页面层级表达信息归属；跳转关系表达任务流，两者不要混用。
- PRD 明确不做的内容仍需记录为 `non-goal`，防止生成时误加功能。
- PRD 要求覆盖某状态但没有视觉方案时，将状态需求标记为 `explicit`，具体表现方案标记为 `proposed`。
- 由常规产品习惯补齐的返回按钮、分页、确认弹窗等，默认是 `inferred` 或 `proposed`。
- 权限、业务口径、敏感字段、真实名称和外部 URL 缺失时，一律 `unresolved`。

## 界面文案分层

从 PRD 提取到的文字先判断它属于哪一层，不能把需求原句不加区分地搬进页面：

- **用户界面文案**：目标用户需要看到的业务信息、操作名称、结果反馈和恢复建议，可以进入 HTML 页面。
- **产品与研发规则**：固定顺序、过滤排序、数量限制、审核与上下线、接口字段、来源参数、版本范围、埋点和兜底策略，只进入 requirement、page spec、annotation 或交付说明。
- **原型说明**：模拟数据、未真实外发、示意素材、未接真实接口等说明默认进入标注或交付文档，不进入业务画布；只有合规要求面向目标用户披露时才作为页面内容。

每条候选可见文案都要通过三个问题：

1. 目标用户是否需要知道这句话，才能理解当前内容或完成任务？
2. 目标用户是否会使用这些词，而不是产品、设计或研发人员才会使用？
3. 删除研发实现细节后，是否仍能清楚说明结果和下一步动作？

任一答案为“否”时，把规则移到页面标注，并为界面改写成用户可理解的内容；不要直接删除背后的需求规则。

## 页面地图确认内容

向产品经理展示：

1. 本轮要生成的页面及父子层级；
2. 主要入口、出口和跨页面跳转；
3. 每页必须覆盖的状态；
4. 已识别但本轮不生成的页面及理由；
5. 会影响页面结构或交互的待确认问题。

只在得到明确答复或已有可追溯确认材料时，将关卡改为 `confirmed`。
